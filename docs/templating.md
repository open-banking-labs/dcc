# Templating

The generators in `dcc-generator` render their output from **Thymeleaf** templates.
The templates are external files, so the shape of generated Java, SQL and documents
can be adjusted — or replaced per deployment — without recompiling Java code.

## Engine

`GeneratorConfiguration` (`dcc-generator`) builds a standalone
`org.thymeleaf.TemplateEngine` (no servlet/web integration) and exposes it as a
`TemplateRenderer` bean.

- **Template mode is `TEXT`.** There is no markup to parse, so values are emitted
  verbatim. Characters such as `<`, `>`, `&` and `"` are **never HTML-escaped** —
  essential for generated code and SQL. (Regression tests assert this.)
- Templates use Thymeleaf's inlined syntax: `[(${expr})]` for unescaped output and
  `[# th:each="x,it : ${list}"] ... [/]` / `[# th:if="${...}"] ... [/]` for control
  flow. `it` is the iteration status (`it.last`, `it.index`, …).

## Built-in templates

Packaged under `dcc-generator/src/main/resources/templates/` (classpath `templates/`),
suffix `.tpl`:

| Template | Produced by | Model variables |
| --- | --- | --- |
| `dto.java.tpl` | `DtoGenerator` | `packageName`, `name`, `fields[{type,name}]` |
| `validation.java.tpl` | `ValidationCodeGenerator` | `packageName`, `className`, `code`, `standard`, `required`, `length`, `regex`, `requiredMessage`, `mismatchMessage`, `lengthMessage` |
| `ddl-create.sql.tpl` | `TableDdlGenerator.generateCreate` | `qualified`, `definitions[{definition}]`, `tableComment`, `columnComments[{column,comment}]`, `indexes[]` |
| `ddl-alter.sql.tpl` | `TableDdlGenerator.generateAlter` | `statements[]` |
| `openapi.json.tpl` | `OpenApiGenerator` | `title`, `version`, `paths`, `schemas`, `mocks` |
| `pom.xml.tpl` | `JarBundleGenerator` | `groupId`, `artifactId`, `version` |
| `artifact-descriptor.json.tpl` | `JarBundleGenerator` | `groupId`, `artifactId`, `version`, `sourceCount` |

For nested/recursive shapes (OpenAPI paths, schemas and mock examples) the fragments
are assembled in Java and injected as pre-rendered values, because their structure
depends on the input fields.

## Overriding the templates

Set `dcc.generator.template-dir` to a filesystem or classpath location. A template
found there **wins** over the built-in one; a template it does not provide falls back
to the bundled default (resolved per template name, so a partial override is safe).

```yaml
dcc:
  generator:
    template-dir: classpath:/templates/   # default
    # template-dir: file:/etc/dcc/templates/   # your overrides
```

Example — a custom `dto.java.tpl`:

```
package [(${packageName})];

// Generated by the Acme style guide.
public record [(${name})](
[# th:each="f,it : ${fields}"]        [(${f.type})] [(${f.name})][# th:if="${!it.last}"],[/]
[/]) {
}
```

Only `dto.java.tpl` needs to exist in the custom directory; the other targets keep
using the built-in templates.

### Supported `template-dir` forms

- `classpath:/somewhere/` — resolved from the classpath (leading slash optional).
- `file:/abs/path/` — a filesystem directory.
- `/abs/path/` or `relative/path/` — treated as a filesystem directory.

## Adding a new generation target

Because rendering is template-first, a new target is a new `.tpl` file plus a thin
generator that supplies its model (or, for a pure template, a `TemplateRenderer.process`
call with a context map) — no change to existing generators.

## Escaping guarantee

`GeneratorTemplates` pins the resolvers to `TemplateMode.TEXT` with
`setForceSuffix(true)`, and `TemplateRenderer` uses `[(${...})]` output. As a result,
identifiers, regexes, comments and SQL literals containing `<`, `>`, `&`, `"` are
emitted unchanged. See `TemplatingRegressionTest.generatedCodeAndSqlAreNotHtmlEscaped`.

## Tests

- `TemplatingRegressionTest` freezes the pre-templating output (`src/test/resources/golden/`)
  and asserts byte-for-byte equality, plus override and non-escaping behaviour.
- `GeneratorWiringTest` proves the renderer, type strategy and generators auto-wire.
